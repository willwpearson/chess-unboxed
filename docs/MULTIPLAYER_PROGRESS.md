# Chess Unboxed — Multiplayer Progress Log

## Goal

Add the multiplayer framework: secure signup/login (already existed, hardened here), private invite-code hosted lobbies, and ranked matchmaking with per-time-control ELO — scoped to the Unboxed (toroidal) variant only. Full plan: `.claude/plans` history / this doc's Key Decisions below. See `docs/CONTEXT.md` for the pre-existing bot-only architecture this builds on.

## Key Decisions (durable — don't re-derive)

- **Realtime transport**: Supabase Realtime (Postgres Changes for game/lobby row updates + Presence) — no Socket.IO, no custom broadcast-from-server calls needed for v1.
- **Migration tooling**: Drizzle, newly wired up (it was a dependency-in-name-only before — `drizzle-kit` scripts existed in `package.json` but no config/schema/migrations existed anywhere). Schema lives in `src/db/schema.ts`, migrations in `drizzle/`. `drizzle.config.ts` reads `DATABASE_URL` (Supabase Postgres connection string — see `.env.example`).
- **Rated games are matchmaking-only** — private lobbies cannot be marked rated in v1 (closes an easy rating-farming/collusion hole between two lobby participants).
- **Move reconstruction strategy: replay-from-move-list, confirmed mandatory (not just the safer option).** Verified `WraparoundChessEngine.fen()` (src/lib/chessEngine.ts) never reflects a wraparound move's board change at all — its internal `chess.js` instance is only touched by `advanceTurn()`, which flips the turn field of a copied FEN and nothing else. So for the whole `'unboxed'` variant, `fen()` always returns the *initial* position with only the turn byte updated, regardless of how many moves have been played. Confirmed live via HTTP smoke test: after two real pawn moves, `games.fen` still read the starting-position FEN. `src/lib/server/gameSession.ts`'s `loadGameManager()` reconstructs purely by replaying `games.moves` through `GameManager.makeMove()` from a fresh game; `games.fen` is written after each move but is a cosmetic/cached field only, never used for reconstruction. Verified via a standalone script that replay reproduces an identical board (including a wraparound pawn capture, e.g. a4xh5) to the live game.
- **Time control buckets**: bullet/blitz/rapid/classical. Matchmaking presets originally decided in Phase 3 (`src/lib/timeControls.ts`): Bullet 60s, Blitz 300s, Rapid 600s, Classical 1800s, all +0 increment — still each bucket's default/first preset, and still what the private-lobby UI's shortcuts source from (`getDefaultPreset`). **Phase 5** widened each bucket to hold a short list of presets (`TIME_CONTROL_PRESETS: Record<TimeControlBucket, TimeControlPreset[]>`, each with a stable `id` like `'blitz-180+2'`) — one alternate increment variant per bucket, to prove out multi-preset pairing without an open-ended matrix. Matchmaking pairing now matches on the exact preset (bucket + seconds + increment), not just the bucket; ELO rating scope is unchanged, still bucket-level only.
- **Matchmaking rating-range widening (Phase 5)**: `src/lib/matchmakingConfig.ts`'s `RATING_BAND_BASE` (100) and `RATING_BAND_WIDEN_PER_SEC` (5) — a ranked candidate's allowed rating gap from the joiner widens the longer *that candidate* has been waiting (`band = BASE + WIDEN_PER_SEC * secondsWaited`, checked in `src/app/api/matchmaking/join/route.ts`'s candidate loop). An out-of-band candidate is skipped (`continue`), not expired, so it stays available for a better-suited future joiner. Finally puts the previously write-only `ratingSnapshot` column to use. Verified live: a >100-point gap built via real decisive games rejects an immediate match but matches after enough real wait time passes for the band to cover it.
- **ELO**: K=40 while provisional (<10 games in that bucket), K=20 at rating ≥2000, K=32 otherwise; standard logistic expected-score formula; pure function in `src/lib/elo.ts` (Phase 3).
- **Ratings are per-`(user_id, time_control)`, not global** (Phase 3: `user_ratings` table) — the existing single `users.current_rating`/`peak_rating` columns predate this and are left alone/unused by the new system. Rows are created **lazily**, only inside `src/lib/server/applyGameResult.ts` when a ranked game between two players actually completes for that bucket — never eagerly at signup for either guests or registered users.
- **Ranked vs. casual matchmaking split** (Phase 3), mirroring Lichess/chess.com: one shared `matchmaking_queue` table and pairing algorithm (`src/app/api/matchmaking/join/route.ts`), differentiated only by `queueType`. `'ranked'` requires a non-guest account and updates ELO; `'casual'` is open to everyone including guests and never touches ratings. `games.mode` extended to `'bot' | 'private' | 'ranked' | 'casual'` accordingly. No background worker/cron exists in this codebase, so pairing is synchronous inside the join request via a two-sided extension of the Phase 2 lobby-join compare-and-swap pattern (claiming an existing waiting row, not just guarding your own insert).
- **`src/lib/jwt.ts`** is now the single source of truth for `JWT_SECRET` (fails fast at import time if unset outside dev mode) and token sign/verify — all auth routes must import from here, never read `process.env.JWT_SECRET` directly or use a hardcoded fallback.
- **`src/lib/rateLimit.ts`** is a single-process in-memory limiter — does not coordinate across multiple serverless instances. Acceptable for now; would need Redis/Upstash to fix properly, out of scope.
- **Abandonment detection (Phase 4): client heartbeat + lazy server-side check**, not a claim-button extension — same "no cron, check lazily on the next request" philosophy as matchmaking-queue/lobby TTL expiry, but driven by the client polling `POST /api/games/[gameId]/heartbeat` (`src/lib/abandonmentConfig.ts`: every 20s) rather than waiting for someone to click something. Works uniformly for timed and untimed games, unlike the pre-existing clock-only `claim-timeout`. A player is forfeited once their `<color>_last_seen_at` (new `games` columns) goes stale past 75s; the surviving player's own heartbeat call is what performs the CAS-guarded forfeit (`src/lib/server/abandonment.ts`), and `applyRankedResult` is invoked identically to any other decisive result.
- **`isWraparound` is only true when a move's raw file distance exceeds 4** (`src/lib/chessEngine.ts`'s `detectWraparoundCharacteristics`) — confirmed via investigation that the wraparound board only ever wraps the file axis, never the rank axis (every move-generation branch applies `% 8` to file only), so whether a move used the wrap path depends solely on file distance, independent of piece type. This replaced a previous hardcoded `true`. **Phase 5** applied the same file-axis-only logic to `wraparoundDistance` (was a mixed file/rank `Math.max`/`Math.min` formula, e.g. wrongly reporting `7` for the canonical `h1→a1` wrap move instead of the true `1`) and `wraparoundPath` (was hardcoded `[from, to]`; now traces real intermediate squares for sliding moves, `[from, to]` still correct as-is for knights since they jump).
- **Simultaneous-both-abandon sweep (Phase 5)**: `sweepAbandonedGamesForUser(userId)` (`src/lib/server/abandonment.ts`), wired into `GET /api/auth/me` — reuses `recordHeartbeatAndCheckAbandonment` unchanged, just calls it for *every* `in_progress` game the caller is party to (not just one game's own heartbeat route). Since `/me` fires on every authenticated page load, a player merely visiting the dashboard (or any page) now sweeps all of their own stale games, closing most of the "both players closed their tab" gap without any cron. New indexes `games_white_player_status_idx`/`games_black_player_status_idx` support the underlying `status='in_progress' AND (white_player_id=? OR black_player_id=?)` query. Verified live: two players both stop calling the game's own heartbeat entirely; the game still flips to `abandoned` purely from one of them calling `/me` after the threshold.

## Open Questions (unresolved — needs input before proceeding)

- [ ] Email provider for password reset, or defer the flow entirely (v1 keeps only the existing logged-in change-password route at `src/app/api/users/change-password/route.ts`). Deliberately left out of Phase 5's scope too.

Closing that completely would need an actual cron/background worker, which this codebase deliberately has nowhere.
